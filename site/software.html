Release Profile

Signing improved. Handoff did not.

PX creates a portable software release pack. Binary, SBOM, provenance, signature — 検証可能な一式にまとめて渡す。受信者はLensを開くだけで、packの検証結果と収録物の対応を確認できる。

バラバラに渡していませんか？

1. binaryとSBOMが別メールで届く

受信者はどのSBOMがどのbinaryに対応するか分からず、確認作業が発生する。

2. provenanceがGitHub UIの奥に埋まっている

ビルドの証明があっても、受信者がたどり着けなければ意味がない。

3. 受け取った人がどこから確認すればいいか分からない

ファイルは揃っていても、検証の起点がないと信頼を確認できない。

署名の上に、受領単位を加える

個別の署名・attestation検証は既にある。一式をまとめて渡し、受信者がオフラインで確認できるhandoff packageが未整備。

1コマンドでパック

px pack --profile=software-release-v1 --evidence=./dist/

Binary、SBOM、provenance、署名をまとめて検証。受信者にはlens-v2.htmlが1つ付く。

$ px pack --profile=software-release-v1 --evidence=./dist/

# Rules: 7/7 passed # Seal: PX-35A3-2026Q1-PASS-7

インストール不要。アカウント不要。オフラインで動く。lens-v2.htmlをブラウザで開けば、packの検証結果と収録物の対応を確認できる。技術的知識は不要。

software-release-v1 プロファイル

何を含めるべきか。何が必須か。プロファイルが定義する。

クラス 必須 検証内容
binary 必須 配布バイナリが1つ以上含まれること
sbom 必須 SPDX or CycloneDX JSON形式であること
provenance 推奨 SLSA provenanceのsubject digestがbinaryのSHA-256と一致すること
signature 推奨 Sigstore bundle or detached signature
changelog 任意 変更履歴
license 任意 ライセンスファイル
vex 任意 脆弱性悪用可能性情報
scan_result 任意 脆弱性スキャン結果（JSON）

必須項目が欠けるとFAIL-CLOSE — packは生成されない。推奨項目が欠けるとWARN — packは生成されるが警告が出る。

GitHub Actionで自動化

リリースワークフローに3行追加するだけ。ビルド後に自動でpackが生成され、リリースに添付される。

# .github/workflows/release.yml - name: PX Pack uses: ./.github/actions/px-pack with: evidence-path: ./dist profile: software-release-v1

Release Lineage（継続した履歴）

parent_manifest_refs[] で前のリリースを参照。受信者は「このv2.1がv2.0の次であること」を検証できる。1回のリリースで終わらない。リリースの連続性を検証可能にし、継続した信頼の履歴を構築する。

EU Cyber Resilience Act（CRA）への備え

EU CRAは2024年12月10日に発効。報告義務は2026年9月11日から、主要義務は2027年12月11日から適用。最大制裁金は1,500万ユーロまたは全世界年間売上高の2.5%のいずれか高い方。SBOMの提供とセキュリティアップデートの追跡が求められる。

✓
SBOM義務

PX packにはSBOM（SPDX/CycloneDX）が必須。形式検証済み。受信者にそのまま渡せる。

✓
脆弱性管理の証跡

VEXとスキャン結果をpackに含めることで、脆弱性対応の証跡を一式で渡せる。

✓
アップデートの連続性

Release Lineageで各バージョンの更新履歴を検証可能に。監査時に「セキュリティアップデートを継続的に提供している」ことの証明になる。
